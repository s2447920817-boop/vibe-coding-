# engineering-review — 工程完备性审查

> 运用钱学森工程控制论（系统论、控制论、信息论）审查软件项目的架构设计、代码框架和工程实践。适用于项目编码前、技术方案评审、或代码审查阶段。

## 触发条件

以下任一情况发生时，**MUST** 调用本 skill：

1. 技术方案初稿完成后，进入编码前
2. 用户说"帮我看看这个架构有没有问题"
3. 代码审查时发现潜在的结构风险
4. 项目上线前，做最后的工程完备性检查
5. 系统出现反复故障，需要系统性复盘

## 输入

- `architecture_doc`: 架构文档路径（如 `architecture.md`）
- `data_model_doc`: 数据模型文档路径
- `api_doc`: API 设计文档路径
- `code_structure`: 项目代码目录结构（可通过 `tree` 或 `ls` 获取）
- `deployment_doc`: 部署文档路径（可选）
- `known_issues`: 已知的工程问题列表（可选）

## 理论基础：钱学森工程控制论三论

钱学森将工程科学的基础归结为三大理论支柱：

| 理论 | 核心思想 | 在软件工程中的映射 |
|---|---|---|
| **系统论** | 系统是由相互联系的要素组成的有机整体，整体功能大于部分之和 | 模块划分、层次结构、耦合度、系统边界 |
| **控制论** | 通过信息反馈实现对系统的调节和控制，使系统达到预期目标 | 监控告警、限流降级、配置管理、异常处理 |
| **信息论** | 信息的获取、传输、处理、存储和利用的规律 | 数据流、接口契约、冗余与缺失、信息安全 |

## 审查维度：12 项检查

### 一、系统论审查（系统是否完整、健壮）

#### 1. 系统边界是否清晰？

**检查点**：
- 系统做什么、不做什么，是否有明确的 Out of Scope 列表？
- 系统与外部世界的接口是否最小化？

**通过标准**：PRD 或技术方案中有明确的边界定义，且每个外部依赖都有替代方案或降级策略。

#### 2. 层次结构是否合理？

**检查点**：
- 是否遵循"上层依赖下层、下层不依赖上层"的原则？
- 是否有清晰的 UI 层、业务逻辑层、数据层、基础设施层划分？

**通过标准**：能用一张图清晰画出数据/控制流的层次，没有跨层调用（如 UI 直接调数据库）。

#### 3. 模块耦合度是否适当？

**检查点**：
- 核心逻辑（如 LLM 调用、数据库操作）是否集中在统一的封装层？
- 修改一个模块是否会影响不相关的模块？

**通过标准**：关键外部依赖（如 AI API、数据库）都有统一的 client/wrapper，不散落在业务代码中。

#### 4. 单点故障是否有预案？

**检查点**：
- 如果某个外部服务挂了，系统还能提供什么级别的服务？
- 如果某个内部模块崩溃了，是否会影响整个系统？

**通过标准**：关键外部依赖有降级策略；内部模块崩溃有隔离机制（如 Promise.allSettled、try/catch 独立）。

#### 5. 系统是否可扩展？

**检查点**：
- 新增一个功能需要改多少文件？
- 新增一个 Agent/角色/模块是否需要改核心代码？

**通过标准**：新增功能主要通过"增加配置"或"新增文件"实现，不需要修改已有核心逻辑。

---

### 二、控制论审查（系统是否可控、有反馈）

#### 6. 是否有反馈机制？

**检查点**：
- 系统运行时，能否知道它在发生什么？（日志、监控、告警）
- 用户操作时，能否知道操作结果？（成功提示、错误提示、加载状态）

**通过标准**：关键路径有日志记录；异常有告警通道；用户操作有状态反馈。

#### 7. 是否有控制输入？

**检查点**：
- 系统行为是否可以通过配置调整，而不需要改代码重新部署？
- 是否有开关可以临时关闭某个功能？

**通过标准**：有环境变量或配置中心管理关键参数（如超时时间、并发数、功能开关）。

#### 8. 异常时是否可控？

**检查点**：
- 系统遇到未预期的输入或外部故障时，是优雅降级还是直接崩溃？
- 用户能否在异常发生后继续操作，而不是被卡死？

**通过标准**：所有外部调用有 try/catch；数据库失败有只读降级；流式中断有保留机制。

#### 9. 目标函数是否清晰？

**检查点**：
- 系统的性能目标是什么？（延迟、吞吐量、可用率）
- 系统的成本目标是什么？（月度预算上限）
- 这些目标是否可衡量？

**通过标准**：PRD 或技术方案中定义了明确的 SLA/SLO，且有监控手段验证。

---

### 三、信息论审查（数据流是否清晰、安全）

#### 10. 信息流是否清晰？

**检查点**：
- 数据从哪来、经过谁、到哪去，是否一目了然？
- 每个数据变更是否有明确的触发者和时间戳？

**通过标准**：能用一张数据流图表达核心数据的生命周期；关键状态变更有审计字段。

#### 11. 信息是否冗余或缺失？

**检查点**：
- 同一份数据是否在多处存储且可能不一致？
- 关键决策所需的信息是否都能获取到？
- 是否有版本控制（如 prompt 快照、配置历史）？

**通过标准**：有单一事实来源（Single Source of Truth）；关键可变状态有快照/历史记录。

#### 12. 敏感信息是否受保护？

**检查点**：
- API Key、密码等凭证是否暴露在客户端或代码仓库？
- 用户数据是否有访问控制？
- 日志中是否包含敏感信息？

**通过标准**：凭证仅在服务端环境变量中；用户输入有校验；日志中敏感信息被脱敏或截断。

## 工作流

### Step 1 — 读取输入

读取所有输入文档和代码结构，建立对项目的整体认知。

### Step 2 — 逐项审查

对 12 项检查点逐一评估，给出：

| 检查项 | 状态 | 证据 | 风险等级 |
|---|---|---|---|
| 1. 系统边界 | ✅/⚠️/❌ | "PRD §7.4 明确列出了 OOS-1~OOS-7" | 低/中/高 |

**状态定义**：
- **✅ 通过**：有明确证据表明符合检查标准
- **⚠️ 警告**：有方案但不完整，或有方案但无证据表明已实施
- **❌ 未通过**：明显缺失或违反检查标准

### Step 3 — 生成报告

```markdown
# Engineering Review 报告

## 1. 项目概况
- 项目名: {name}
- 审查日期: {date}
- 审查范围: {architecture + data-model + api + code}

## 2. 系统论审查

### ✅ 通过的项
- 系统边界: PRD §7.4 明确列出 7 项 Out of Scope
- 层次结构: 前端 → API Routes → lib/orchestrator → lib/llm + lib/db

### ⚠️ 警告的项
- 单点故障: 仅有 Kimi 一个模型供应商，未设计模型切换 fallback
  - 建议: 在 LLM client 层抽象 provider 接口，为 FR-204（多 provider 切换）预留结构

### ❌ 未通过的项
- 反馈机制: 无自动化监控告警，仅依赖 Zeabur 日志面板和手动巡检
  - 建议: MVP 阶段至少配置 Kimi 余额不足告警；Phase 2 接入 Sentry

## 3. 控制论审查
...

## 4. 信息论审查
...

## 5. 风险汇总与修复优先级

| 优先级 | 检查项 | 修复建议 | 预估工时 |
|---|---|---|---|
| P0 | 反馈机制 | 配置 Kimi 告警阈值 | 10 分钟 |
| P1 | 单点故障 | 抽象 LLM provider 层 | 2 小时 |
| P2 | 可扩展性 | 将 Agent 排序逻辑从硬编码改为配置驱动 | 1 小时 |

## 6. 审查结论

- **是否可以通过技术方案评审**: {是/否，附条件}
- **是否适合上线**: {是/否，附条件}
- **下一步必须完成的动作**: {清单}
```

### Step 4 — 输出修复任务

对每一个 ❌ 和 ⚠️，生成可执行的修复任务，包含：
- 具体文件路径或文档章节
- 修改建议（可直接作为 Edit 的 old_string / new_string）
- 优先级和预估工时

## 防退化规则

1. **MUST NOT** 因为"业界最佳实践"而提出与项目规模不匹配的审查要求（如要求个人项目做完整的混沌工程）。
2. **MUST** 区分"架构设计问题"和"实现细节问题"——本 skill 只关注前者，代码风格等由 linter 处理。
3. **MUST** 每个 ❌ 都给出至少一条可执行的修复建议，不能只指出问题不提供方案。
4. **SHOULD** 对警告项（⚠️）给出"如果不修复，最坏情况下会发生什么"的场景描述，帮助用户理解风险。
5. **MUST NOT** 审查用户已经明确接受的风险（如 PRD 中已声明"无访问控制，用户已知风险"）。
