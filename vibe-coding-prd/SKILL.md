# vibe-coding-prd —— Vibe Coding PRD 撰写规范

> 传统 PRD 写给程序员看，论证"为什么要做"。Vibe Coding PRD 写给 AI 看，指令"怎么做、不做什么、怎么验证做对了"。

## 一、核心定位

| 维度 | 传统 PRD | Vibe Coding PRD |
|---|---|---|
| **读者** | 开发团队 | AI（Claude / Kimi / Cursor 等） |
| **目的** | 争取资源、对齐认知 | 直接生成可执行代码 |
| **内容重心** | 市场分析、用户痛点、商业价值 | 功能边界、数据流、状态规范、验收标准 |
| **决策主体** | 人（PM 和开发协商） | AI 自动推断，人只需确认 |
| **变更成本** | 低（口头对齐即可） | 高（改 PRD = 改代码逻辑） |

**一句话原则**：Vibe Coding PRD 是一份"代码生成指令书"，而不是"产品论证书"。凡是 AI 写代码时不需要知道的信息，都不要写。

---

## 二、5 个必写模块

### 模块 1：产品定义（Product Definition）

**定义**：用 3 句话以内说清楚"这是什么产品、给谁用、解决什么问题"。

**为什么必须有**：AI 在生成代码前必须理解业务上下文。一个错误的理解会导致整段架构偏离方向，后期返工成本极高。

**一句话检验**：如果 AI 读了这 3 句话后，仍然不知道"用户在什么场景下打开这个网页"，就说明没写清楚。

---

### 模块 2：功能边界（Feature Boundaries）

**定义**：明确列出"必须做、以后做、绝不做"三件事，并为每项分配稳定 ID。

**为什么必须有**：AI 没有"常识"和"分寸感"。你不说"不做"，它就会做；你不说"必须"，它就可能遗漏。边界不清是 vibe coding 中返工的第一大原因。

**一句话检验**：如果 AI 读完功能边界后，仍然问"这个要做吗"，就说明边界没划清。

---

### 模块 3：页面与数据流（Pages & Data Flow）

**定义**：列出所有页面/模块，描述数据从哪来、经过谁、到哪去、存在哪。

**为什么必须有**：AI 需要知道"系统有哪些组成部分"以及"它们如何协作"。没有这个，AI 会写出数据流混乱、状态管理失控的代码。

**一句话检验**：如果画不出一张简单的数据流图，说明页面与数据流没想清楚。

---

### 模块 4：交互与状态规范（Interaction & State Spec）

**定义**：描述用户怎么操作、系统怎么响应、所有边缘状态（空态/加载态/错误态/成功态）长什么样。

**为什么必须有**：AI 写 UI 时默认只考虑"理想路径"。空页面、网络断开、输入错误这些状态如果不明确规定，AI 一定会遗漏，上线后全是 bug。

**一句话检验**：如果每个页面没有至少 3 种状态定义（正常 + 空态 + 错误），说明状态规范不完整。

---

### 模块 5：验收标准（Acceptance Criteria）

**定义**：每个 MVP 功能"怎么算做对了"的量化标准，包括正面场景和负面场景。

**为什么必须有**：vibe coding 没有 QA 团队，PRD 必须自带测试标准。否则 AI 认为"编译通过"就算完成，而产品经理认为"完全不是我要的"。

**一句话检验**：如果一条验收标准无法通过"操作一遍就能验证"，就说明不够量化。

---

## 三、模块填写规则（含正反例）

### 模块 1：产品定义

#### 必填内容

| 子项 | 规则 | 正例 | 反例 |
|---|---|---|---|
| **一句话定义** | ≤30 字，不含技术术语 | "一个让个人用户管理每日待办的极简网页工具" | "一个基于 React + Node.js 的全栈待办管理系统" |
| **三句话扩展** | 谁用 + 什么问题 + 怎么解决 | "职场人士每天事务繁杂，容易遗漏；本产品通过极简的输入和清晰的分类，帮助用户 3 秒内记录一个任务" | "我们希望打造行业领先的待办产品，通过 AI 赋能提升用户效率..." |
| **成功指标** | 3-4 个，可衡量 | "新用户 30 秒内完成第一个任务创建" | "提升用户满意度" |
| **项目代号** | 英文小写 + 连字符 | `simple-todo` | "待办大师 V1.0" |

#### 状态定义

```markdown
## 1. 产品定义

### 1.1 一句话定义
一个让个人用户管理每日待办的极简网页工具。

### 1.2 三句话扩展
1. 目标用户是事务繁杂的职场人士和自由职业者。
2. 他们现在用纸笔或备忘录记录待办，容易遗漏且难以追踪完成状态。
3. 本产品提供比备忘录更专注的待办体验：打开网页 → 输入任务 → 完成标记，全程不超过 3 次点击。

### 1.3 项目代号
`simple-todo`

### 1.4 成功指标
| 指标 | 目标值 | 验证方式 |
|---|---|---|
| 首次创建任务耗时 | ≤30 秒 | 手动计时 |
| 页面首屏加载 | ≤2 秒 | Lighthouse |
| 任务完成率 | 用户创建的任务中 70% 被标记完成 | 数据库统计 |
```

### 模块 2：功能边界

#### 必填内容

| 子项 | 规则 | 反例（常见错误） |
|---|---|---|
| **MVP（必须做）** | 没有就不叫产品；每项必须有稳定 ID（如 `FR-001`）；用动词开头 | "更好的用户体验"（不是功能） |
| **Phase 2（以后做）** | MVP 跑通后再做；同样分配 ID；标注依赖关系 | 把"用户登录"放在 Phase 2（如果产品是多人用的，登录是 MVP） |
| **明确不做（绝不做）** | 超出边界的功能；每项必须给出"为什么不做的理由" | 只写"不做"不给理由，后期容易争论 |

#### ID 规则

- 格式：`{模块缩写}-{3位数字}`，如 `FR-001`、`UI-003`
- 前缀：
  - `FR` = Feature（功能）
  - `UI` = User Interface（界面）
  - `API` = API 接口
  - `NFR` = Non-Functional Requirement（非功能需求）
- ID 一旦分配，永久不变。废弃项保留 ID，标注 `[Deprecated]`。

#### 状态定义

```markdown
## 2. 功能边界

### 2.1 MVP（v0.1）—— 没有就不叫产品

| ID | 功能 | 规则说明 |
|---|---|---|
| FR-001 | 创建任务 | 输入框 + 回车，任务立即出现在列表顶部 |
| FR-002 | 标记完成 | 点击任务左侧复选框，任务文字变灰并移至列表底部 |
| FR-003 | 删除任务 |  hover 任务右侧显示删除按钮，点击后无确认直接删除 |
| FR-004 | 任务列表展示 | 未完成任务在上，已完成任务在下，按创建时间倒序 |
| FR-005 | 数据持久化 | 刷新页面后任务不丢失（浏览器 localStorage 即可） |

### 2.2 Phase 2（v0.5）—— MVP 跑通后再做

| ID | 功能 | 依赖 | 理由 |
|---|---|---|---|
| FR-006 | 任务分类（工作/生活） | FR-001 | 需要先有任务，才能分类 |
| FR-007 | 截止日期提醒 | FR-001 | MVP 阶段用户手动管理时间即可 |
| FR-008 | 多设备同步 | FR-005 | 需要后端和用户系统，MVP 只单设备 |

### 2.3 明确不做（Out of Scope）

| ID | 功能 | 不做理由 |
|---|---|---|
| OOS-001 | 用户注册/登录 | 个人工具，localStorage 足够，增加登录会降低首次使用转化率 |
| OOS-002 | 任务优先级排序 | 与"极简"定位冲突，增加认知负担 |
| OOS-003 | 分享/协作功能 | 目标用户是个人管理，非团队协作 |
| OOS-004 | 数据导出/备份 | MVP 阶段数据量小，Phase 2 再评估 |
```

### 模块 3：页面与数据流

#### 必填内容

| 子项 | 规则 |
|---|---|
| **页面清单** | 名称、路径（如 `/`）、职责、是否需要登录 |
| **导航关系** | 用户如何从 A 页面到 B 页面（点击、跳转、返回） |
| **数据流** | 核心数据的生命周期：谁创建 → 存在哪 → 谁读取 → 谁修改 → 谁删除 |
| **外部依赖** | 调用了哪些第三方服务（如 AI API、地图、支付），以及 fallback 策略 |

#### 正反例

**反例**（只列页面，没有数据流）：
```markdown
页面：首页、任务列表页、设置页
```

**正例**（页面 + 数据生命周期）：
```markdown
### 3.1 页面清单

| 页面 | 路径 | 职责 | 登录要求 |
|---|---|---|---|
| 任务首页 | `/` | 展示任务列表、创建新任务 | 不需要 |

### 3.2 导航关系
```mermaid
flowchart LR
    A[打开 / ] --> B[任务首页]
    B -->|点击复选框| B
    B -->|点击删除| B
```

### 3.3 数据流

**任务数据（Task）生命周期**：
1. **创建**：用户在输入框输入文字，按回车 → 前端生成 Task 对象（id, text, completed, createdAt）
2. **存储**：写入浏览器 localStorage，key = `simple-todo-tasks`
3. **读取**：页面加载时从 localStorage 读取，解析为列表渲染
4. **更新**：点击复选框 → 修改 completed 字段 → 写回 localStorage
5. **删除**：点击删除按钮 → 从数组移除 → 写回 localStorage

### 3.4 外部依赖

| 服务 | 用途 | 是否必须 | Fallback |
|---|---|---|---|
| 无 | — | — | — |
```

### 模块 4：交互与状态规范

#### 必填内容

对每个**关键页面/组件**，必须定义以下状态：

| 状态 | 触发条件 | UI 表现 | 用户操作 |
|---|---|---|---|
| **正常态** | 有数据且网络正常 | 正常展示 | — |
| **空态** | 无数据 | 不能空白，必须有引导 | 引导用户创建第一条 |
| **加载态** | 数据正在获取 | 骨架屏或 loading 指示器 | 不可操作，防止重复提交 |
| **错误态** | 请求失败/数据异常 | 明确错误信息 + 重试入口 | 可点击重试 |
| **成功态** | 操作成功 | 短暂成功提示，自动消失 | 无需操作 |

#### 核心交互流写法

按"用户做了什么 → 系统做了什么 → 用户看到什么"三步写：

```markdown
### 4.1 创建任务交互流

**步骤 1：用户聚焦输入框**
- 用户做了什么：点击输入框或页面加载后自动聚焦
- 系统做了什么：输入框获得焦点，显示闪烁光标
- 用户看到什么：输入框边框变为高亮色（主色）

**步骤 2：用户输入并提交**
- 用户做了什么：输入任务文字，按回车（或点击"添加"按钮）
- 系统做了什么：
  1. 验证：非空校验（空内容不提交，输入框轻微抖动提示）
  2. 生成 Task 对象（id = 时间戳，completed = false）
  3. 插入列表顶部
  4. 清空输入框
  5. 写入 localStorage
- 用户看到什么：新任务以动画形式出现在列表顶部，输入框清空并保留焦点

**步骤 3：用户标记完成**
- 用户做了什么：点击任务左侧复选框
- 系统做了什么：
  1. 切换 completed 状态
  2. 任务文字添加删除线，颜色变灰
  3. 延迟 300ms 后，任务以动画形式移动到列表底部
  4. 写入 localStorage
- 用户看到什么：任务视觉上"下沉"到已完成区域

### 4.2 状态规范

#### 空态（无任务时）

| 维度 | 规范 |
|---|---|
| 触发条件 | 任务列表为空（首次访问或全部删除） |
| UI 表现 | 页面中央显示大图标（勾选框轮廓）+ 文字"今天还没有任务，创建一个吧" |
| 用户操作 | 点击输入框直接开始创建 |

#### 错误态（localStorage 写入失败）

| 维度 | 规范 |
|---|---|
| 触发条件 | localStorage 写入抛出异常（如存储空间满） |
| UI 表现 | 页面顶部显示横幅错误："保存失败，请清理浏览器存储空间后重试" |
| 用户操作 | 点击横幅上的"重试"按钮 |
```

### 模块 5：验收标准

#### 必填内容

| 子项 | 规则 | 反例 |
|---|---|---|
| **正面场景** | 正常操作流程，必须量化 | "用户可以创建任务"（无法验证） |
| **负面场景** | 异常输入/异常状态，AI 最容易遗漏 | 不写错误场景 |
| **边界场景** | 空值、超长、特殊字符 | 不写边界 |

#### 量化标准

每一条验收标准必须能通过"操作一遍 + 观察结果"来验证，不能模糊。

```markdown
## 5. 验收标准

### 5.1 功能验收（FR-001 ~ FR-005）

| ID | 场景 | 操作步骤 | 期望结果 |
|---|---|---|---|
| AC-001 | 创建任务（正常） | 1. 打开首页<br>2. 输入"买牛奶"<br>3. 按回车 | 1. 列表顶部出现"买牛奶"<br>2. 输入框清空<br>3. localStorage 中有该任务 |
| AC-002 | 创建任务（空内容） | 1. 聚焦输入框<br>2. 直接按回车 | 无任何反应，不创建空任务 |
| AC-003 | 创建任务（超长） | 输入 500 个字符后按回车 | 任务被截断至 200 个字符后创建，或不允许输入超过 200 字符 |
| AC-004 | 标记完成 | 点击未完成任务左侧复选框 | 1. 文字变灰+删除线<br>2. 300ms 后移动到列表底部 |
| AC-005 | 取消完成 | 点击已完成任务的复选框 | 任务恢复到未完成列表顶部 |
| AC-006 | 删除任务 | 鼠标 hover 任务，点击右侧删除图标 | 任务从列表和 localStorage 中移除，无确认弹窗 |
| AC-007 | 刷新持久化 | 1. 创建一个任务<br>2. 刷新页面 | 任务仍然显示在列表中 |
| AC-008 | 空态展示 | 首次打开页面（无历史数据） | 显示空态插图和引导文字，不显示空白列表 |

### 5.2 性能验收

| ID | 指标 | 目标值 | 验证方式 |
|---|---|---|---|
| AC-009 | 首屏加载时间 | ≤1.5 秒 | Chrome DevTools Network 面板 |
| AC-010 | 创建任务响应 | 按下回车后 ≤100ms 出现 | 肉眼感知即时 |

### 5.3 兼容性验收

| ID | 场景 | 期望结果 |
|---|---|---|
| AC-011 | Chrome / Edge / Safari / Firefox 最新两版 | 功能正常，样式无错乱 |
| AC-012 | 移动端浏览器（iOS Safari / Android Chrome） | 可以正常使用，输入框自动聚焦 |
```

## 四、解耦管理策略

Vibe Coding PRD 的 5 个模块在逻辑上是一个整体，但在物理文件上**必须解耦**，以便：
- 修改设计时不触动功能边界
- AI 可以按需读取子文档，减少上下文消耗
- 多人协作时不产生冲突

### 推荐文件结构

```
project-root/
├── docs/
│   ├── PRD.md              # 模块 1 + 2 + 5（产品定义、功能边界、验收标准）
│   ├── interaction.md      # 模块 3 + 4（页面、数据流、交互、状态规范）
│   ├── design-system.md    # 设计规范（颜色、字体、组件）
│   ├── api-design.md       # API 接口文档（如有后端）
│   └── data-model.md       # 数据模型（如有数据库）
└── README.md               # 项目入口 + Quick Start
```

### 解耦规则

| 规则 | 说明 | 正例 | 反例 |
|---|---|---|---|
| **引用不嵌套** | PRD 中不贴大段其他文档的内容，只放链接/引用 | "讨论气泡组件详见 [design-system.md §3.2]" | 把 design-system 整段内容复制到 PRD 中 |
| **单向依赖** | 子文档可以引用 PRD，PRD 不依赖子文档的具体内容 | interaction.md 引用 PRD 中的 FR ID | PRD 写"按钮圆角 8px"（应放到 design-system） |
| **ID 全局唯一** | FR / AC / UI 等 ID 全局唯一，跨文档可追踪 | PRD 引用 `FR-003`，interaction.md 也引用 `FR-003` | 不同文档各自编号 |
| **变更日志独立** | 每份子文档维护自己的变更日志 | PRD.md 有 §10 变更日志，design-system.md 也有独立变更日志 | 只在 PRD 中记录所有变更 |

### 小型项目（单文件模式）

如果项目极小（如单页面工具），可以把 5 个模块合并到一份 `PRD.md` 中，但**模块之间用标题严格分隔**，便于 AI 按模块检索：

```markdown
# simple-todo · PRD

## 1. 产品定义
...

## 2. 功能边界
...

## 3. 页面与数据流
...

## 4. 交互与状态规范
...

## 5. 验收标准
...
```

## 五、完整示例

以下是一个完整的小型项目 PRD，涵盖全部 5 个模块。

```markdown
# 极简待办 · 产品需求文档（PRD）

---
version: v0.1.0
date: 2026-05-04
status: 待开发
---

## 1. 产品定义

### 1.1 一句话定义
一个让个人用户管理每日待办的极简网页工具。

### 1.2 三句话扩展
1. 目标用户是事务繁杂的职场人士和自由职业者。
2. 他们现在用纸笔或备忘录记录待办，容易遗漏且难以追踪完成状态。
3. 本产品提供比备忘录更专注的待办体验：打开网页 → 输入任务 → 完成标记，全程不超过 3 次点击。

### 1.3 项目代号
`simple-todo`

### 1.4 成功指标
| 指标 | 目标值 | 验证方式 |
|---|---|---|
| 首次创建任务耗时 | ≤30 秒 | 手动计时 |
| 页面首屏加载 | ≤2 秒 | Lighthouse |
| 任务完成率 | 70% 的任务被标记完成 | 数据库统计 |

## 2. 功能边界

### 2.1 MVP（v0.1）

### 3.3 数据流

**Task 生命周期**：
1. 创建：用户输入 → 前端生成 {id, text, completed, createdAt}
2. 存储：写入 localStorage（key: `simple-todo-tasks`）
3. 读取：页面加载时解析并渲染

5. 删除：从数组移除 → 写回

## 七、常见错误与修正

| 错误 | 后果 | 修正 |
|---|---|---|
| "用户可以轻松创建任务" | AI 无法判断什么叫"轻松" | "输入任务文字，按回车，任务出现在列表顶部" |
| "支持多种登录方式" | 范围模糊，AI 可能实现 5 种 OAuth | "MVP 仅支持邮箱+验证码登录，明确不做微信/QQ/微博登录" |
| 不写空态 | AI 生成空白页面，用户体验极差 | 为每个列表/内容区定义空态 |
| 不写错误态 | 出错时页面崩溃或无任何提示 | 为每个外部调用定义错误态 |
| PRD 里写"按钮用主色 #FFD700" | 设计细节混入 PRD，修改时牵一发动全身 | 移到 design-system.md，PRD 只写"按钮用主色" |
| 功能 ID 不唯一 | 模块间引用混乱 | 全局统一编号，废弃保留标记 |

## 九、工作流（如何调用本 Skill）

### 触发条件

以下任一情况发生时，**MUST** 调用本 skill：

1. 用户说"我想做一个...""帮我写个 PRD""给我一份需求文档"
2. 用户有一个产品想法，但还没有结构化的需求描述
3. 用户已有草稿 PRD，要求"完善/重写/补全"
4. 新增功能模块，需要扩展现有 PRD

### 执行步骤

1. **理解产品**：从用户描述中提取产品定义（一句话 + 三句话）
2. **追问澄清**：如果用户描述模糊，用以下问题追问：
   - "这个产品的核心用户是谁？"
   - "用户现在不用这个产品时，是怎么解决这个问题的？"
   - "做到什么程度你会觉得这个项目成功了？"
   - "有什么功能是明确不做的？"
3. **生成功能边界**：区分 MVP / Phase 2 / 明确不做，分配 ID
4. **推导页面与数据流**：基于功能边界，推导需要哪些页面和数据流
5. **定义交互与状态**：为每个页面定义核心交互和 3+ 种状态
6. **编写验收标准**：为每个 MVP 功能编写可验证的验收标准
7. **解耦检查**：确保设计细节和技术细节没有混入 PRD
8. **输出自查清单**：让用户逐项确认

## 十、防退化规则

1. **MUST NOT** 在 PRD 中写技术实现细节（如"用 React useState 管理"）——那是技术方案的事。
2. **MUST NOT** 在 PRD 中写视觉细节（如"按钮用 16px 圆角"）——那是设计规范的事。
3. **MUST** 给每个功能项分配稳定 ID，废弃的项保留 ID 并标 `[Deprecated]`。
4. **SHOULD** 在"明确不做"列表中给出"为什么不做的理由"，防止需求蔓延。
5. **MUST** 在变更日志中记录每次修改（版本号、日期、改动内容）。
6. **MUST NOT** 因为"感觉重要"而增加第 6 个必写模块。5 个模块是 vibe coding 的最小可用集合，额外内容应放到子文档。
7. **MUST** 确保每条验收标准可以通过"操作一遍"来验证，不允许模糊描述。
