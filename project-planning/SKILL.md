# project-planning — 项目文档与项目规划

> 根据项目类型、团队规模、时间线，判断需要输出哪些文档、不需要哪些文档，并设计清晰的文档架构。适用于 vibe coding 场景下的项目启动阶段。

## 触发条件

以下任一情况发生时，**MUST** 调用本 skill：

1. 用户问"这个项目需要写哪些文档"
2. 用户问"还缺什么文档"
3. 用户说"帮我规划一下这个项目的文档结构"
4. 项目启动时，作为第一步确定"文档范围边界"
5. 项目中期，用户感觉"文档太多太乱"，需要重新梳理

## 输入

- `project_type`: 项目类型（`personal-tool` / `internal-tool` / `small-team-toc` / `enterprise` / `ai-product`）
- `platform`: 目标平台（`web` / `ios` / `android` / `mini-program` / `cross-platform`）
- `team_size`: 团队规模（`solo` / `2-5` / `6-15` / `16+`）
- `has_designer`: 是否有专职设计师（`yes` / `no`）
- `has_qa`: 是否有专职 QA（`yes` / `no`）
- `timeline`: 时间线（`1-week` / `1-month` / `3-month` / `6-month+`）
- `existing_docs`: 已存在的文档列表（可选）

## 核心判断矩阵

### 文档必要性矩阵

| 文档 | 个人/内部工具 | 小团队 toC | 中大型企业 | AI 产品特有 |
|---|---|---|---|---|
| BRD | ❌ | △ | ✅ | △ |
| 竞品分析 | △ | ✅ | ✅ | ✅ |
| 立项决策 | ❌ | △ | ✅ | △ |
| MRD | ❌ | △ | ✅ | △ |
| 用户调研 | △ | ✅ | ✅ | ✅ |
| **PRD** | ✅ | ✅ | ✅ | ✅ |
| 用户故事 | ❌ | △ | ✅ | ❌ |
| **功能清单** | ✅ | ✅ | ✅ | ✅ |
| **交互原型** | ✅ | ✅ | ✅ | ✅ |
| 高保真 | ❳ | ✅ | ✅ | ❳ |
| **设计规范** | ✅ | ✅ | ✅ | ✅ |
| **技术方案** | ✅ | ✅ | ✅ | ✅ |
| **API 文档** | ✅ | ✅ | ✅ | ✅ |
| Agent 设计 | ❌ | ❌ | ❌ | ✅ |
| 测试用例 | ❳ | △ | ✅ | △ |
| 评测体系 | ❌ | ❌ | ❌ | ✅ |
| 评测集 / bad case | ❌ | ❌ | ❌ | ✅ |
| 发布 checklist | △ | △ | ✅ | △ |
| 运营计划 | ❌ | ✅ | ✅ | △ |
| 数据分析 | ❳ | ✅ | ✅ | ✅ |

**图例**：
- ✅ **必须有** — 缺少会导致项目无法落地或后续维护困难
- △ **建议有** — 有则质量更高，没有也能跑
- ❳ **合并到其他文档** — 不需要独立文件，作为其他文档的一个章节
- ❌ **不需要** — 在 vibe coding 场景下属于流程冗余

### 合并规则（❳ 的处理方式）

| 文档 | 合并到 | 合并后位置 |
|---|---|---|
| 用户故事 | PRD | PRD §4 功能清单的每个功能项描述中 |
| 高保真（无设计师时） | 设计规范 | 设计规范中增加"参考实现截图"章节 |
| 测试用例（无 QA 时） | 技术方案 / 兜底策略 | 技术方案 §兜底策略 或 PRD §7 |
| 数据分析（立项时） | PRD §1.4 成功指标 | 在成功指标中定义数据埋点需求 |
| 发布 checklist | 部署文档 | deployment.md §发布前检查 |

## 工作流

### Step 1 — 项目类型诊断

根据输入参数，确定项目落入哪个象限：

```
                  有专职设计师
                       ↑
    小团队 toC ←───────┼───────→ 中大型企业
    (敏捷迭代)         │         (流程规范)
                       ↓
                  无专职设计师
    个人/内部工具 ←────┘         AI 产品
    (vibe coding)                 (需要评测)
```

### Step 2 — 生成最小可用文档清单

基于诊断结果，从矩阵中提取 ✅ 和 △ 的文档，按优先级排序：

| 优先级 | 文档 | 理由 |
|---|---|---|
| P0 | PRD.md | 项目宪法，所有决策的唯一权威来源 |
| P0 | 交互原型/线框图 | 确认 UX 流，防止开发后返工 |
| P0 | 技术方案 | 确定架构方向、技术选型、目录结构 |
| P0 | API 设计 | 前后端契约，防止接口扯皮 |
| P0 | 数据模型 | 数据库设计，数据结构一旦定下来很难改 |
| P1 | 设计规范 | 视觉一致性，有设计师时必须；无设计师时可用参考素材替代 |
| P1 | 部署文档 | 怎么上线、环境变量、FAQ |
| P1 | 兜底策略 | 出错怎么办（可合并到 PRD 或技术方案） |
| P2 | 竞品分析 | 帮助产品决策，但非工程阻塞 |
| P2 | 成本估算 | 防止上线后账单惊吓 |
| P2 | 测试策略 | 无 QA 时可简化，但不能完全不管 |

### Step 3 — 文档架构设计

为项目设计文档目录结构，给出两种模式：

**模式 A：文档集中（适合小团队）**
```
project-root/
├── docs/
│   ├── PRD.md              # 产品宪法（含功能清单、交互、兜底策略）
│   ├── design-system.md    # 设计规范（或指向 Figma 链接）
│   ├── tech-spec.md        # 技术方案（含架构、数据模型、API）
│   └── deployment.md       # 部署指南
└── README.md               # 项目入口 + Quick Start
```

**模式 B：文档分散（适合中大型团队）**
```
project-root/
├── docs/
│   ├── product/
│   │   ├── PRD.md
│   │   ├── user-research.md
│   │   └── competitive-analysis.md
│   ├── design/
│   │   ├── interaction.md
│   │   └── visual-spec.md
│   └── engineering/
│       ├── architecture.md
│       ├── api-design.md
│       ├── data-model.md
│       └── test-strategy.md
├── README.md
└── deployment.md
```

### Step 4 — 输出项目规划报告

```markdown
# Project Planning 报告：{项目名}

## 1. 项目诊断
- 类型: {project_type}
- 平台: {platform}
- 团队规模: {team_size}
- 时间线: {timeline}

## 2. 最小可用文档清单

### P0（必须有，阻塞级）
- [ ] PRD.md
- [ ] {交互原型/线框图}
- [ ] {技术方案}
- [ ] {API 设计}
- [ ] {数据模型}

### P1（建议有，质量级）
- [ ] {设计规范}
- [ ] {部署文档}
- [ ] {兜底策略}

### P2（加分项，可选）
- [ ] {竞品分析}
- [ ] {成本估算}
- [ ] {测试策略}

## 3. 不需要的文档（明确排除）

| 文档 | 排除理由 |
|---|---|
| BRD | 个人项目，口头决策即可 |
| 用户故事 | PRD 功能清单已覆盖，独立文档增加维护成本 |
| ... | ... |

## 4. 推荐的文档架构

{模式 A 或 B 的目录树}

## 5. 下一步行动建议

1. 先写 PRD.md（项目宪法）
2. 再写交互原型（确认 UX）
3. 同步确定技术方案（防止 PRD 中的需求技术不可行）
4. 最后写部署文档和兜底策略
```

## 防退化规则

1. **MUST NOT** 因为"流程要求"而强迫写不需要的文档。每份文档都必须能回答"不写它会导致什么决策失误"。
2. **MUST** 在报告中明确标注"不需要的文档"及其理由，防止团队成员后续补充冗余文档。
3. **SHOULD** 建议把测试策略、发布 checklist 合并到技术方案或部署文档中，而不是独立成文。
4. **MUST** 区分"文档"和"记录"：竞品分析、用户调研是**记录**（做完就归档），PRD、技术方案是**文档**（持续维护）。记录不需要变更日志，文档需要。

## 决策点

| 场景 | 处理方式 |
|---|---|
| 用户坚持要写矩阵中标记 ❌ 的文档 | 尊重用户选择，但在报告中标注"流程冗余，建议合并" |
| 项目从"个人工具"演进为"小团队 toC" | 触发一次重新规划，把 △ 升级为 ✅ |
| 团队有专职设计师但没有专职 QA | 高保真设计稿必须有，测试用例合并到技术方案 |
| AI 产品但团队没有 AI 背景 | 必须增加评测体系（即使团队小），否则上线后无法判断 Agent 质量 |
